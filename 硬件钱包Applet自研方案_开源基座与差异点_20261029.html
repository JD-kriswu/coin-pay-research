1 · 信任边界总图（修正版）

分层标准不变：这层交到别人手里，他能不能冒充我们、碰用户的钱或数据？能 → 自己握；不能 → 可买/合作，但必须能审计。相对原版图的修正：① 第 6 层补充"卡厂定制 applet"第三条路（飞天模式）；② 卡间备份协议从第 4 层拆出，归入 applet 规格项。

层性质内容与厂商
1. App 端 + 清晰签名自己做交易构造、多链、防盲签、地址与账户管理。自建。
2. 品牌与账户后端自己做账户体系、固件分发、客服运营入口。云设施可买（AWS），逻辑自控。
3. 用户身份数据 命门自己握终端用户 PII 不进代工厂，境外自控设施，与代工厂物理隔离。
4. 找回信任模型 + SOP 命门自己握谁持哪片、兜底路径、身份核验/冷静期/申诉。MPC 组件可选 Fireblocks/Web3Auth。
5. 设备真伪密钥 (attestation) 命门自己握发卡根密钥自己生成、HSM 保管，绝不进代工厂。
6. 卡内签名 applet买/合作三条路：① fork status-keycard（Apache-2.0）自研适配；② Satochip 开源基座（AGPL 传染）；③ 飞天等卡厂按我方协议定制（原版图"中国卡厂无一家能自研"修正为"无现成钱包 applet 产品可授权，但可定制代工"）。硬性准入：开源 + 可复现构建 + 第三方审计。
7. 安全芯片 (SE)买同心微 THD89（国产 EAL6+，secp256k1 需实测）/ 汇顶 eSE / NXP / 英飞凌 / 三星。
8. 结构件/组装/物流外包深圳供应链。只做壳与组装，安全层（6/7）绝不交给只会做卡的厂。

私钥在第 7 层芯片内生成、永不出芯片——全图没有"我们保管用户私钥"这一层。混合托管（2-of-2 服务端联签）如果上，属于第 2 层自控后端的规则，不改边界。

2 · 开源基座选型

项目规模/LanguageLicense活跃定位
keycard-tech/status-keycard15 个 Java 文件Apache-2.0 ✅持续维护（2026-10 有 push，★264）首选基座。以太坊钱包卡完整实现，Status App 百万级用户在用。商用无传染。
Toporin/SatochipApplet模块化 JavaAGPL-3.0 ⚠️活跃（★178）备选。BTC 系，Electrum 集成 6 年+。AGPL 传染：网络交互也触发开源义务，闭源商用基本不可行，只作交叉参考。

选型结论：fork status-keycard。Apache-2.0 是三者中唯一可闭源商用的；模块切分教科书级（一个钱包 applet 的全部 = 15 个文件）；SecureChannelV2 / SECP256k1 / attestation 齐全。Satochip 的价值在"另一个角度的实现"用于交叉验证安全逻辑，不作基座。

3 · Applet 主要逻辑（15 文件全拆解）

KeycardApplet.java ← 主入口：process(APDU) 命令分发状态机 ├─ 密钥生命周期 种子生成/导入、BIP32 派生、私钥不可导出 ├─ 签名服务 收 hash → 门卫检查 → 芯片内 ECDSA → 返回签名 ├─ SecureChannelV2 卡-App 会话加密：ECDH → HKDF → AES-CCM + 计数器防重放 ├─ SECP256k1.java secp256k1 软实现（多数 JCOS 不原生支持，自己算） ├─ IdentApplet 设备身份 + attestation（出厂密钥签名） ├─ NDEFApplet NFC 碰一碰弹 URL（开箱引导） ├─ Capabilities 版本协商（卡能力位） ├─ CashApplet 支付场景实验模块 ├─ InstallTask 装载流程（install() 预分配全部对象——JCOS 无 GC） └─ LockTask 锁定（错误计数 → 锁死）

逻辑浓缩：5 个模块 + 1 条命

模块职责来源
① 密钥保险库私钥芯片内生成、派生、签名；任何指令读不出明文。卡的灵魂。抄 Keycard
② 签名门卫什么状态可签、要不要 PIN、错误几次锁卡。防盲签是安全核心。自己写（差异点）
③ 安全信道指令在手机-卡之间的窃听/篡改/重放防护。抄 SecureChannelV2
④ 状态机+事务出厂→初始化→活跃→锁死；JCSystem.beginTransaction() 原子写。抄
⑤ 认证与身份PIN 管理 + 出厂 attestation。抄 + 对接自有根密钥
一条命：install() 预分配所有对象。JavaCard 无 GC，运行时 new = 死。这是 JavaCard 与普通 Java 最大的心智差异，Keycard 全程遵守——改动时也必须遵守。

业务逻辑边界（架构原则）

卡不认识区块链：收到 32 字节 hash，签名返回 64 字节 r||s。UTXO/gas/链规则全在 App。但有三类"看起来像业务"的安全逻辑必须在卡内：签名授权门卫（②）、派生路径白名单（只允许标准路径，防主密钥导出）、密钥用途分离（签名密钥不得用于认证）。

5 · 需要自己做的部分

#事项量级说明
1差异代码：支付授权门卫几百行 + 设计限额状态机、服务端授权证明的卡内校验（验签+防重放）。新增 APDU 指令。
2差异代码：卡间备份协议2-3 周组建立（验真→签字→盖章→ECDH 传种子密文）、中途加卡、密码轮换。Keycard 没有，照 Tangem 公开协议重实现。
3信任根建设密钥仪式 + HSM发卡根密钥生成/保管/注入流程。第 5 层命门，一行开源代码替不了。
4产线对接2-3 个月飞天 pre-personalization：GP SCP03 真密钥轮换、逐卡唯一密钥注入、卡面/包装。开发卡（40..4F 公开测试密钥）→ 量产卡两条世界。
5App + SDK 适配数月（非本方案重点）NFC 会话、交易构造、防盲签 UI。宿主 App 已有，接 SDK 层。
6验证闭环持续jcardsim 仿真 → 真卡测试（算法矩阵/时序）→ 第三方审计（管别人的钱，从第一天按可审计标准写）。
开源基座给的是"发动机"（会写），剩下的是"车队"（发行）。类比验证：Tangem App+SDK 全开源仍活得好——壁垒在卡商关系、信任根、产线、审计、运营，不在代码。Keycard 把 applet 从"2 年自研"压缩到"4-8 周适配"，但第 1-5 层（App/后端/数据/找回/真伪密钥）一行开源代码都替不了。

6 · 路线图与验证清单

里程碑

  1. W1-2 基座跑通：clone status-keycard → jcardsim 仿真跑全流程 → 淘宝开发卡（¥200 级）真卡装载（GP 测试密钥）
  2. W3-6 差异开发：支付授权门卫 + 卡间备份协议（jcardsim 先行，真卡验证）
  3. W7-8 信任根：发卡根密钥仪式（HSM）+ attestation 链打通（IdentApplet 对接自有根）
  4. M2-M3 产线：芯片选型实测（THD89 secp256k1 / JCAlgTest 矩阵）→ 飞天 pre-personalization 试产小批量
  5. M3+ 审计与发行：第三方审计（applet 几百行，审计便宜一个量级）→ 试点发行

验证清单（不可跳过）

  • secp256k1：JCAlgTest 算法矩阵 + 真卡跑 BIP32 测试向量，不能只看 EAL6+ 证书（国产卡算法支持参差）
  • 装载：开发卡公开测试密钥 40..4F 阶段不放任何真资产；SCP03 真密钥在 pre-personalization 后独有
  • 防篡改四道门核对：SCP03 装载 / JCOS 防火墙 / 物理 EAL5+/6+ / attestation+DAP
  • 代码红线：不动 SecureChannelV2 计数器语义；install() 预分配原则不破坏；软实现密码原语不做侧信道优化（宁可慢）
